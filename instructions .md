Goal
The broad goal of the major project is to explore the replicability of some existing resources that have been made available, in the spirit of open science and reproducible research.  The first part of this will involve reading a description of the work, typically in the form of an academic paper; installing and running code that has been made available with the paper; and applying the code to the original data to see if the results in the description of the work hold.  The second part will involve creating new data to which the code can be applied, and see if the claim(s) made by the original work still holds.

Examples
We discuss three examples of this in weeks 2 and 3.

Text Segmentation
The academic paper is the one released in week 1, on Bayesian Unsupervised Topic Segmentation; if you look up the original source, you'll see that it appeared in a good Natural Language Processing (NLP) conference, EMNLP (CORE ranking A*, Google Scholar venue ranking #2 in computational linguistics).  In the week 2 exercise, you'll be downloading the code into a virtual machine and running it on sample original data.  Creating new data will be the goal of one of the workshops later in the course.

Privacy-Preserving Text Representations
The academic paper is the one released in week 2, called "Towards Robust and Privacy-preserving Text Representations"; the original source appeared in the top NLP conference, ACL (CORE ranking A*, Google Scholar venue ranking #1 in computational linguistics).  I discuss the replication of the work in terms of code and original data in week 2, along with the extension to new data.

fastText Text Classification
The description of the technique used by the fastText system appeared in several conferences; the references at the link only give the arXiv source, but they also appeared in good conferences, and are highly cited (e.g., Bojanowski et al (2016) has around 1730 citations according to Google).  In the week 2 exercise you'll be installing the code in a virtual machine. Then you'll be working through the tutorial on text classification, applying the code to the original data for the tutorial.

Project Format
Project Type
There will be two versions of the project: the default project, where you will work with one of the projects we propose; and the novel project, where you will find and justify your choice of paper + code + original data.  

You may choose to do the default project if you wish.

For a novel project, it can be easy to choose something that is too difficult or infeasible (because existing models turn out to be unavailable, or more resources are necessary than are available via your VMs or notebooks, or ...).  The first assessment, the project proposal, is your opportunity to propose a novel project; we will then assess it for feasibility.  If you cannot convince us that your initial novel project is feasible, you should do the default project.

The requirements will be mostly the same for default and novel projects.  The default project, however, will have a maximum mark of 80% for the project assessment tasks.  This is because there is no choosing and justification for the project topic.  More details are available in the guidelines for each assessment task.

Project Assessment Items

There are three components to the project: a project proposal (worth 20%), an update presentation (40%) and a final report (40%).

Assessment Criteria
The project should explicitly incorporate techniques and tools covered during the unit.  A key part of the assessment will be based on a github repository in the submission, which should include, e.g., the final report, new data created during the project, scripts for creating new data, etc.  The following are criteria which will be explicitly considered in the assessment:

Justification for project basis: This will consider how well the paper, code and original data are explained and justified (e.g., the source conference and its quality, etc).  This only applies to novel projects, not the default project.  As justifications for quality of source, work, consider the CORE rankings and Google Scholar discipline rankings (choosing probably an appropriate subcategory under Engineering and Computer Science), and/or number of citations (or possibly a secondary source, like research.com's ranking of computer science conferences).

Explicit inclusion of unit techniques and tools: This will consider the extent to which the unit techniques and tools are incorporated into the project.  For example, the use of scripts to gather data from the Internet, carry out data analysis, and generate new data.  The project does not have to incorporate every topic covered in the unit, but should manage several.

Success in replication and investigation of original work: This concerns getting original code working on original data, and getting something like the original results.  (In some cases -- e.g., if there's a mistake in the original work -- it might not be possible to get the original results, but the project report should contain evidence of investigating this.  Also, resource constraints may limit the replication to only a subset of the results.  This is fine, but some justification should be given.)  This criterion further involves digging into the original results, by for example presenting and discussing examples where the paper's method works or does not work, etc.

Quality of new data and code: It is not necessary to produce industrial-strength code, but it should be readable and be able to be run by me.  The new data should aim for similar quality to the original data, subject to limitations (e.g., we won't have money to pay for crowdsourced annotation labels).

Quality of report or presentation: The report / presentation should be polished, contain all the necessary components, and be clearly presented.

For each of the separate assessment items (i.e., the project proposal, the project update presentation,  and the final report), there will be a marking rubric that relates to these criteria.
